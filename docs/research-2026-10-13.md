# Deep research: where colony-kernel actually stands (2026-10-13)

Four papers, read in full, not skimmed. Each one is either direct evidence for
the premise colony-kernel is built on, or a competitor that has already shipped
something adjacent. Budget: 1 search round + 2 extracts, well under the daily
cap.

## Status since 2026-10-13

The tree now runs 135 deterministic tests, up from the 121 it ran on the
research date. The independent review completed on 2026-10-05. Milestone 1A
passed with two low-severity findings. F1, the human-authority guard's
empty-list precondition, is closed at the application layer. F2 was a
recorded observation with no severity. That clears the R8 precondition, so M2
adapter work may start, though M2 itself is unimplemented and unreviewed.
Items 1, 2 and 3 of "What I would do next" are therefore done: the README,
the landing page and the distribution posts now name Arbiter-K and Rel(AI)Build,
and the README and the landing page cite the 3% number. Item 4, an evaluation
of our own, is still open.

## 1. "False success" is a measured, named failure, and it is huge

**Paper:** *From Confident Closing to Silent Failure: Characterizing False
Success in LLM Agents* (arXiv 2606.09863v1)

This is the paper that validates the premise. It names our problem and puts
numbers on it.

| Finding | Number |
|---|---|
| False success as a share of **all failures**, tau2-bench single-control | **44–52%** |
| Same, in a dual-control domain (independent user simulator can verify state) | **3%** |
| AppWorld, agents with explicit completion claims | **75.8%** |
| Per-model spread within a single benchmark | **13% → 89%** |
| Best LLM judge AUROC (5 judges × 5 prompts × full task spec) | **0.65** |
| Same judges on AppWorld API traces | **0.54** |
| Simple TF-IDF detector, task-disjoint AUROC, tau2-bench | **0.83** |
| Same, AppWorld | **0.95** |
| Detector latency vs an LLM judge call | **3,300× faster** |

**The single most important number here is the 3%.** When an *independent*
verifier can check state, false success collapses by an order of magnitude.
That is not a mitigation. It is a mechanism, and it is exactly the argument
colony-kernel makes. "Models propose, only the kernel commits" is the 3% case.

**Second important number: judges cap out at AUROC 0.65.** An LLM judge reading
a trajectory cannot reliably tell success from false success, because the
surface signal false success exploits *is* the signal judges use to infer
completion (confident closing language). Trajectories with assertion vocabulary
score 0.27–0.36 points more "completed" regardless of outcome.

**The uncomfortable part.** An adversarial rewrite test took 50 honest-failure
trajectories and rewrote only the closing message in confident-completion style.
The XGBoost detector flipped on 20% of them; GPT-4o and Claude Sonnet 4.5 each
flipped on 24%. Even the detectors that beat judges are gameable by prose
alone. This is the strongest argument for colony-kernel's position.
**If the signal lives in natural language, it is attackable. The decision has to
be made on programmatic state.** Which is what the kernel does.

**What this costs us to claim.** The paper says lightweight detectors are the
right production monitor, not that a kernel is. We are making a stronger claim
(state, not text, is the substrate) and we should be honest that this paper
supports the premise without validating the specific architecture.

## 2. The verification status gets laundered away in ordinary handoffs

**Paper:** *Silence Is Endorsement: Verification-Status Laundering in LLM Agent
Pipelines* (arXiv 2609.20211)

A different failure with the same root. A claim survives a pipeline hop; the
fact that it was never verified does not.

| Finding | Number |
|---|---|
| Risky-action approval, marker kept vs removed, Llama-3.1-8B | **5% → 60%** |
| Same, Qwen2.5-14B | **9% → 98%** |
| Full proposer→summarizer→memory→monitor pipeline, 3 monitors | **57–81% approval** |
| Does instructing the monitor to distrust unverified claims fix it? | **No**: over-refuses legitimate work on some models, still vulnerable on others |

**Why this matters to us specifically.** The last row is the finding that
justifies colony-kernel's design over the obvious alternative. The obvious fix
is "tell the agent not to trust unverified claims." That was tested. It fails,
inconsistently, across models. The paper's conclusion is that authorization
provenance must be **structured state attached to the claim** throughout the
pipeline.

That is what colony-kernel's content-addressed approvals are: a SHA-256 bound
to a specific transition, consumed exactly once, expired at commit. The
verification status is not prose that a summarizer can drop. It is state the
kernel holds.

**Honest caveat.** The paper's fix is "structured state"; it does not propose a
kernel. And one of its own results cuts against over-confidence in structure.
In the structured-survival control, whether a JSON status field survives a
summarizer hop depends entirely on *which* summarizer (0.10 preserved by one,
0.85 by another). Structure alone is not a guarantee. Colony-kernel's answer is
that the kernel, not the pipeline, holds the state, but that claim needs its
own evidence.

## 3. Someone already shipped the deterministic kernel idea

**Paper:** *From Craft to Kernel: A Governance-First Execution Architecture and
Semantic ISA for Agentic Computers* (**Arbiter-K**, arXiv 2604.18652v1)
Code: `github.com/cure-lab/ArbiterOS`

This is the finding that should change how we talk about colony-kernel.

Arbiter-K's premise, verbatim in the paper: delegating the system control loop
to LLMs is "a fundamental category error by treating the Large Language Model as
the core of the system control loop." Their fix: reify probabilistic messages
into discrete instructions (a Semantic ISA), run them through a deterministic
neuro-symbolic kernel, propagate taint along data-flow pedigree, and interdict
at deterministic sinks.

| Finding | Number |
|---|---|
| Unsafe interception, two agent systems | **76% → 95%** |
| Absolute gain over native policies | **92.79%** |
| Success rate of SOTA models on complex real-world tasks (their cited baseline) | **as low as 30%** |
| Malicious instructions bypassing text-based defenses | **>40%** |

**What this means, stated plainly.** "Models propose, only the kernel commits"
is not a novel thesis in 2026. Arbiter-K published it, with a working
implementation, better numbers than ours, and an OS-level ambition (it targets
taint tracking and architectural rollback, which colony-kernel does not
attempt).

**Where colony-kernel can still differ.** Arbiter-K is security-first: taint,
sinks, interception of unsafe trajectories. Colony-kernel is *mission*-first: a
22-stage state machine, budget ledgers, approvals bound to transitions, durable
rejections. The overlap is the deterministic kernel; the substance is different.
But we cannot claim to be first to the idea, and any post that implies it will
not survive contact with someone who has read this paper.

**Action this implies.** As of this research the README and the site both lead
with "the problem" and never name the adjacent work. That is fine for a first
read, but the distribution posts should acknowledge Arbiter-K by name rather
than let a reader discover we did not. Being the person who cites the
competitor is cheaper than being the person who got caught not knowing.

## 4. A control plane with the same mechanisms, measured on 10,008 repos

**Paper:** *A Deterministic Control Plane for LLM Coding Agents*
(**Rel(AI)Build**, arXiv 2606.26924v1)

Same architectural conclusion, different evidence base, plus a prevalence study
that is directly relevant to how colony-kernel itself should be governed.

| Finding | Number |
|---|---|
| Repos surveyed / agent config files | **10,008 / 6,145** |
| Config paths that are **exact SHA-256 duplicates** across independent repos | **10.1%** |
| Duplicate pairs crossing organisational boundaries | **75.5%** |
| Configs with a single commit (never revised) | **58%** |
| Agent configs declaring permission boundaries | **<1%** (vs 33% of Actions workflows) |

Their proposed control plane maps one-to-one onto those gaps: SHA-256 content
addressing, HMAC-stamped lockfiles, hash-chained audit logs, tiered permissions
before LLM invocation, a phase state machine with requirement→file→test
traceability, one canonical definition compiled to seven IDE targets.

**Two things worth taking.**

1. **Content-addressing is the convergent answer.** Two independent papers land
   on SHA-256 over canonical bytes as the way to make agent configuration
   trustable. Colony-kernel already does this for approvals. The 10.1%
   duplicate-config finding is a *prevalence* argument we could cite. It is
   measured on 6,145 real files, not asserted.

2. **Their honesty about scope is worth copying.** The abstract says explicitly:
   "Determinism applies to install-time gates, blocklists, and phase-state
   transitions; trace linkage is cooperative and auditable post-hoc, **not
   pre-execution enforced**." That is the same disclosure colony-kernel's README
   makes about M1A. Papers that scope themselves precisely get cited; papers
   that overclaim get caught.

## What this research actually changes

| Before | After |
|---|---|
| "The problem is unverified agent claims" | It is measured at 44–52% of failures, and an independent verifier cuts it to 3%. We can cite a number. |
| "LLM judges are unreliable" | AUROC 0.65 cap, mechanism identified. Not opinion. Measured. |
| "Telling the agent to distrust unverified claims would work" | Tested and failed across models. Structured state is required. Our architecture is the justified one. |
| "We have a novel thesis" | **We do not.** Arbiter-K shipped the deterministic-kernel argument first, with better numbers. Cite it. |
| "Content-addressing is our design choice" | Two independent papers converge on it. Cite the prevalence study for why. |

## The honest gaps in our position

1. **No evaluation of our own.** Arbiter-K reports 76–95% interception. As of
   the research date colony-kernel reported 121 deterministic tests, which
   prove the kernel behaves as specified, not that it catches false success in
   the wild. We have no number equivalent to theirs.
2. **The adversarial rewrite result cuts both ways.** 20–24% of prose-rewritten
   failures fool even the good detectors. If our verification ever rests on
   reading agent language rather than state, we inherit that 20–24%.
3. **M2 is unblocked but unimplemented.** The independent review completed on
   2026-10-05, which clears R8 for starting M2. M2 itself is unimplemented and
   has to come back for its own review before merge. Until it runs, our
   correctness claim is about the kernel, not about outcomes.

## What I would do next, in order

1. **Name the adjacent work in the distribution posts.** Arbiter-K and
   Rel(AI)Build get one sentence each in the X thread and the HN post. It costs
   nothing and it is the difference between a serious project and a project
   that got found out.
2. **Add the 3% number to the README's problem statement.** "When an independent
   verifier checks state, false success drops from 44–52% of failures to 3%"
   is the single strongest argument for the architecture, and it is not ours.
   It is measured.
3. **Do not claim novelty.** Claim *scope*: mission-control with budgets,
   approvals and durable rejections, versus their security interceptions.
   Different axis, same kernel idea.
4. **The real gap is an evaluation.** Everything else is polish. A benchmark
   that shows colony-kernel refusing an agent's false completion claim would be
   the first number that is actually ours.
